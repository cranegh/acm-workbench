# 个人题解风格

## 先读原作，再读本题

以仓库根目录为基准，优先阅读用户editorials已有的题解：

如：
- `editorials/abc475-E.md`
- `editorials/icpc-2026-online2-K.md`

学习已有题解的风格。
随后阅读目标代码、题面与限制，检查已有同题文章。没有题面且关键条件无法确认时，先取得必要信息，不编造背景或证明。

## 写成用户自己的推理节奏

- 用直接、自然的中文，允许朴素口语。围绕“先想到什么 → 为什么不够 → 关键观察 → 如何实现”讲清楚，不堆术语、套话或夸张评价。
- 篇幅跟随内容。简单的关键转化可以是几条思路、复杂度和代码；确有曲折的题再展开朴素解法、突破、代码细节和真实踩坑。不强制每篇套同一组标题。
- 先讲改变解法的观察，再解释实现。式子只用于澄清关系，给关键结论必要的理由，不凭感觉跳到答案。
- 使用用户代码里的变量名和实际数据结构。需要时截取短代码解释状态含义、分支和边界，避免每行代码都翻译一遍。
- 保留用户的解题方式与代码风格。不要为了文章漂亮重写整份代码或替换算法。发现实质错误时先指出并验证，不把有问题的实现包装成正确答案。
- 根据实现计算复杂度；例如 `map` 和哈希表的开销需要区分，不能直接照搬原作或口头算法的结论。说明必要的前提与边界。

## 心路历程必须真实

当文章适合复盘且用户未提供经历时，可以在选题后合并询问：

> 这道题你最初怎么想、主要卡在哪里、最后是什么观察让你想通的？有印象的错误或调试过程也可以说，没有就按算法推导来写。

- 使用用户实际回答，不擅自添加情绪、时长、比赛情境、提交次数或“我一开始……”的故事。
- 未取得个人经历时写“直接模拟需要……”“关键观察是……”，不把代码推断写成用户亲历。
- 用户说记不清或直接写时继续客观推导；已经提出问题且还在等回复时，不自行假定答案或抢先定稿。
- 不照抄参考文中的个人经历、错误或口头禅。借鉴表达节奏，不复制故事。

## 成文与核验

- 沿用 `editorials/` 的 Markdown 和文件命名习惯；标题准确，需要时给已核实的原题链接。已有同题文章优先补充，避免另写一份重复内容。
- 根据题目需要安排：必要题意、思路推导、关键实现、复杂度、代码。篇幅长时可用简短自然的小标题；总结只写真正值得记住的点，不重复全文。
- 代码以本轮用户实现为基础，展示代码或引用文件应能对应实际版本。任何修正明确说明，不默默改变原解法。
- 核对题意、约束、推导、数据结构开销、代码与边界；样例或测试只有实际运行过才能写通过，不能从文件名或注释推断已 AC。
- 仅写有沉淀价值的题，不机械产出日报，不重复生成索引。完成后将文件交回维护流程，由主技能处理整体检查和 Git 同步；本技能不独立 commit 或 push。
